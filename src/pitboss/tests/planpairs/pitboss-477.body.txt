### PR 477: safety analysis (CAST) and the design that leaves no gap to find

Written 2026-11-12, fourth version (earlier: `cast-477-final-1.md` to `-3.md`). Code read: pitboss main 482a642 and branch b6985a2. **What the programs in `cast-sets/final/` are.** They are prototype programs written to measure the design: a verdict, the act verbs, the readers and writers, and the tests over them. They run on fake GitHub worlds, on real read-only data and on real git in scratch directories. They are not pitboss. **PR 477 puts this behaviour into pitboss**, with these tests as its tests (section 8). Every number below is from running the prototypes; one command re-runs them all, and the outputs are in `cast-sets/final/out/`:

`sh /mnt/project-files/pitboss/cast-sets/final/RUN.sh`

Nothing was written to GitHub or to any repository.

The owner's rulings this version is built on:

* **Agents told to use `pitboss act` use it.** There is no token split, no read-only identity, no credential check and no barrier around agents. The design makes the right path complete and correct, and keeps forgetting out.
* **477 does not merge with a hole.** Completeness is a test in 477's own CI (`pitboss nox`). The PR cannot be green with an uncovered state, an unrouted line, a write without a verb or a text its reader reads differently. Nothing is left to be found after the merge, and nothing here leads to another pitboss ticket.
* **GitHub's documented schema and behaviour are stable.** The sets are derived from them once and frozen. No control, test or text here is about GitHub changing.
* **Mutants run in CI only, and Plan commands are run as written.** There is no sandbox. 477 removes the pitboss command that runs mutants, so none can run on a host.
* **All of it is one PR.**

### 3. The control structure

| Controller | Control actions | What it believes | Feedback |
|---|---|---|---|
| Owner | Rulings in chat, tickets, holds | The queue as reported | Chat, PR pages |
| Coordinator (Opus) | Relays rulings | Rulings as remembered (62 relays on 477) | Hand-backs |
| Orchestrator | Dispatch, review requests, merge, arm, undraft, label | pitboss's printed step and its own memory | `pitboss sweep` |
| pitboss | Prints a step | The fields and events its code happens to read | GitHub reads |
| Workers, reviewers | Push, PR body, review comment, hand-back | The brief | CI, review text |
| GitHub | Merge, queue, CI runs | Own state | n/a |

### 5. The design

#### 5.1 One path: act verbs (kind A)

A verb reads the state, runs the verdict, writes, and reads back. The agent supplies only the intent. The verbs: merge, arm, disarm, undraft, review, label, hold, unhold, block, override, ticket, ticket-edit, close, comment, pr-create, pr-edit, update-branch, rerun, cancel, dispatch-workflow, push, clean, dispatch-next.

Completeness of the verb set is derived from the actions, in two directions:

* **From the tools.** The session's tool list has 48 GitHub tools; 24 write. Twelve have a verb. The other twelve (`push_files`, `delete_file`, `fork_repository`, `sub_issue_write` and so on) were used 0 times in 51,933 recorded calls, so no step of the work needs them (`cover_writes.out`).
* **From pitboss.** Of its 39 commands, 11 reach a GitHub write by call graph; each has a verb (`cover_commands.out`).

What the verbs do that a printed step cannot:

| Verb | What it holds | Cases |
|---|---|---|
| merge, arm, undraft | Hold check and verdict in the same call as the write | G2, G3, G21, S04, S23 |
| hold, block, label `paused-owner` | Disarm auto-merge on the PRs they cover, so an armed PR is always one the verdict passes | G18, X27, G14 |
| push | The assigned branch, a commit with a change, a pre-push check that printed `ok`, then `ls-remote` shows the commit | G22, G23, G25, X34 |
| clean | A worktree with a commit on no remote branch is kept | X35 |
| dispatch-next | Slots are the config's, the cap holds, the oldest unfinished PR first, a red shared by PRs or by the base is one ticket, a refused plan-check goes back to its worker | G1, G13, G16, S16, S17, S19, X25, X26 |
| override | Lifts one named stop line for one head, with a reason. Never a failed check or status, a hold, a block, a closed PR, a failed read | G4, G27, X31 |

#### 5.2 A total verdict (kind B)

* Every PR field of the schema has a row. A field with no rule has a row that says so by name (`milestone`, `stack`).
* Every documented timeline kind is in exactly one class: benign, or "after the review, so review again".
* Two changes at once behave as their union (`cover_pairs.py`): over 74,991 pairs, no value hides another's stop and no pair gives a line without a route. The 8,199 pairs left out change the same input, which holds one value at a time.
* Every documented value of each enum the verdict branches on (check conclusion, check status, status state, mergeable state) is in a named table with its meaning.
* Passing is an allowlist: a check passes on `success`, `neutral`, `skipped`; a status on `success`. Everything else is red or waiting.
* The review binds the head and digests of the body, of the Plan section and of each ticket, so an edit after approval makes the review stale without a rule per kind of edit (G6, G24).
* Block records and `Blocked` lines are read with the state of what they name (G14, X32).

#### 5.3 Verbs write the texts; instructions come from the checker (kind C)

* `act review` writes the review. A review typed as a comment is not read. So `Plan: ok`, `Plan: approved.` and a prose Plan line (G7, G9, G12, G17, X28) have no way to be written.
* `act ticket` writes the ticket; the reader takes list items, or paragraphs when there is no list, and never a key line (G26, X29). Of 378 real tickets with a Done-when heading it reads 329; the 49 others are rewritten by `act ticket` before dispatch (`corpus_tickets.out`).
* `act pr-create` and `act pr-edit` check the body rows before writing (G8, G11).
* The hand-back has one line per Done-when item: `done` with a GitHub URL or path, `impossible` with the command and its output, or `owner` with a request and a recommended answer (G16).
* `total.instructions()` is the text the brief and skills carry. It is built from the route table, so each actor is told the verb and the form the checker requires. The brief adds every rule file whose `paths:` match the ticket's paths, in full, and the verdict's gates on those paths (G15, G20, G28; 68 real rule files, 0 refused).

#### 5.4 Every line has a route (kind D)

`total.ROUTES` maps each stop line to an actor and a verb. Counted over the 219 distinct lines of the enumeration: none is without a route, and none says pitboss does not know something. On the 134 real merged PRs, the verdict gives 251 stop lines: 102 to the worker, 99 to the reviewer, 48 to the orchestrator, 2 to pitboss itself (read again), 0 to the owner.

* Rulings are cases (`rulecases.py`): a world, an action, the expected verdict. A new ruling that no encoding satisfies together with the old ones is refused when it is recorded, as one question (G10). Dropping a case needs a record of which ruling wins.
* Mutants run only in the CI job, on its ephemeral runner. In 477 the `mutation-check` command is removed from pitboss's command list; the mutant runner is the CI job's own step and has no local mode and no root flag. The check `no_local_mutants.py` finds a registered command that runs mutants: on branch b6985a2 it is red (`src/pitboss/mutation_commands.py:180`), and on a tree without the registration it is green (case G29). Plan commands are run by plan-check as written.

### 6. Why 477 merges with no gap left

A gap is a state in which pitboss's output is wrong or missing. It needs one of four things to be true. Each is false by construction, and a test in 477's CI is red if it becomes true, so the PR cannot merge with it.

| A gap needs | Why it cannot hold | The CI test, and the planted hole that turns it red (`test_total.out`) |
|---|---|---|
| A write with no verb | The verb set covers every write tool that was ever used and every writing command | `cover_writes`, `cover_commands`; "a verb a route names is removed" |
| A state the verdict does not read | The verdict has a row for every field of GitHub's schema and a named meaning for every documented value, alone and in pairs | `cover2`, `cover_pairs`; "a timeline kind of the frozen list is in no class", "a check conclusion ... in no table", "a mergeable_state ... in no table", "a documented kind is dropped from its class" |
| A text read differently than written | The writer and the reader are run against each other | "`act review` writes a form the verdict does not read", "the ticket reader reads what `act ticket` writes differently", "the reviewer's instruction does not name `act review`" |
| A line with no step | Every line the verdict can emit, over the whole enumeration, has a route | "the route of a body stop is removed", "a row that says pitboss does not know comes back", "a repository has a label pitboss does not apply" |

The sets are complete because they are GitHub's own: the PR object's 49 fields, the 46 timeline kinds, the values of each enum, the 48 GitHub tools of the agent session and pitboss's 39 commands. They are derived by script from GitHub's documentation and frozen in the PR; the re-derivation gives the same bytes. GitHub's schema is stable, so the frozen sets are the whole input space of pitboss, at the merge and after it.

Rulings are the other input. A ruling is recorded as a case. If it contradicts an earlier one, the recording is refused with the question, at the moment of the ruling (G4, G10). It does not surface later as a PR with no route.

So when 477 is green: there is no write outside a verb, no field or value without a meaning, no hand-typed text that pitboss parses, and no line without a route. Each of these four statements is a test that was run with a planted hole and went red. That is what the thirteen post-mortems lacked: a claim of closure was never a test.

### 9. Rulings that conflict

Each is one question with the answer the prototype encodes.

**Q1. "pitboss is not the final arbiter: you have to run it, but you can override it if there's a reason" (2026-11-04) against a verdict that stops.**
Proposed: the override is the verb `act override` (the stop line, the reason). It lifts that one line for that head. It never lifts a failed check or status, a hold, a block, a closed PR or a failed read (cases G4, G27, X31).

**Q2 (B2). After a Plan is approved, what follows the first Execution "changes needed"?**
Proposed: one fix round when every finding is mechanical and named; otherwise `paused-owner`.

**Q3 (B4). Quarantining a failing test:** quire's e2e rule requires `test.fixme('#N')` in the filing commit; C14 forbids any skip.
Proposed: allowed in quire e2e only, with the ticket number. `rulecases` picks this encoding when both cases are kept (case G10).

**Q4 (B3). Does a coordinator relay use up a PR's one ruling?**
Proposed: no. Only a posted `Opus ruling` comment counts.

**Q5 (B5). How is "the test fails on main" shown?**
Proposed: no run on main. Each test plants the violation and the removal check shows the control is what refuses it, as this document does.

**Q6 (B8). Does the pre-push hook run the full `pitboss nox`?**
Proposed: only checks that finish in about a minute and print `ok`; nox is CI's. `act push` requires the `ok` (case G25).

**Q7 (B6). When does 477's worker resume?**
Proposed: when this document is accepted, on section 8.

Answered by the owner on 2026-11-12 ("all work must be done in one PR"): B1 (a gap found during 477 goes into 477) and B7 (#444 stays one PR). "Nothing is added to a started PR" keeps 477 as its one stated exception.
